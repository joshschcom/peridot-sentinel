# Sentinel vault factory bytecode budget

**Keep the deployed vault sibling at its pinned version for the December 2 freeze.** Its factory has 180 bytes of runtime headroom. The account it creates has 3,992 bytes. For a subsequent version that needs another vault operation, separate the account creation image from the factory’s executable code while retaining constructor-initialized accounts. A private fork test reproduced the existing account runtime exactly with this arrangement. The prototype is confined to the measurement fixture. [Vault deployment](../packages/chain-config/expansion/deployments/vault-1952.json) · [Measurements](../evidence/session7-size/measurements.json)

## Where the limit applies

EIP-170 caps the runtime bytes returned by each contract creation at 24,576. EIP-3860 separately caps the creation program, including ABI-encoded constructor arguments, at 49,152 bytes where that rule is active. These are per-contract limits. A transaction gas increase cannot enlarge either budget. [EIP-170](https://eips.ethereum.org/EIPS/eip-170) · [EIP-3860](https://eips.ethereum.org/EIPS/eip-3860)

| Pinned contract | Runtime bytes | Runtime headroom | Creation bytes before arguments | Argument bytes | Complete initcode bytes |
|---|---:|---:|---:|---:|---:|
| Base v2 account, `81fb457` | 14,502 | 10,074 | 16,590 | 160 | 16,750 |
| Base v2 factory, `81fb457` | 17,853 | 6,723 | 18,313 | 96 | 18,409 |
| Vault v2 account, `a48f203` | 20,584 | 3,992 | 23,548 | 192 | 23,740 |
| Vault v2 factory, `a48f203` | 24,396 | 180 | 24,835 | 128 | 24,963 |

The factory’s `new VaultSentinelAccountV2(...)` embeds the entire 23,548-byte child creation program at offset 795 in factory runtime. Only 848 bytes of that runtime sit outside the child image. Adding a selector or a constructor check on the child can exhaust the parent’s budget before the child approaches its own runtime cap. Both official testnet RPCs matched all four public runtime lengths and manifest hashes at block 47,249,530. Constructor immutables were masked only when comparing live bytes with the uninstantiated compiler template. The full on-chain bytes were hashed for comparison with the manifest. ## Deployment choices

| Choice for a new version | Measured effect or bound | Trade-off |
|---|---|---|
| Tune compiler optimization | At one optimizer run, vault factory runtime falls to 24,347 bytes and account runtime to 20,546. The factory gains 49 bytes, for 229 free. | Different bytecode and runtime identities require fresh manifests and verification. Benchmark operation gas before adopting any settings change. This saving provides little feature capacity. |
| Move validation or quoting into a typed external contract | Size savings depend on what moves. The existing `SingleVaultAdapter` already performs identity, capacity and preview checks externally. | Safe for side-effect-free reads from pinned code. Keep permission checks, recipient restrictions, budget charges, approvals and settlement-delta checks with the asset-owning account. Extra calls consume gas and introduce a dependency whose failure behavior needs testing. |
| Put a typed `new Account(...)` in an external deployer | That deployer must itself return runtime containing the 23,548-byte creation image and its own creation logic. Its current maximum available overhead is 1,028 bytes. | Reduces the registry factory’s size but moves the tight boundary to another contract. If used, give the factory sole access to a fixed deployment route and pass the original owner explicitly. |
| Store reviewed creation bytes in two immutable code fragments | Prototype factory runtime **1,198 bytes**, headroom **23,378**. Two data contracts each have **11,775 bytes** of runtime, including a leading STOP. Factory initcode including arguments is **26,004 bytes**. Account size and constructor match the original. | Two additional creations at factory deployment. Each account creation copies and hashes the bytes. The EIP-170 limit still applies to each fragment and the account. The factory and account must still fit their individual initcode limits. |
| ERC-1167 initialized clones | A standard clone has 45 bytes of runtime delegating to one fixed implementation. The factory would deploy clone code in place of the full account creation image. An implementation still has its own 24,576-byte budget. | A larger design change to ownership, storage initialization, code identification, operation gas and the project’s delegation policy. No clone deployment or gas measurement is claimed here. [ERC-1167](https://eips.ethereum.org/EIPS/eip-1167) |

### Constructor image split

The new factory’s constructor builds the original child creation image once and puts each half behind a STOP instruction at a separate address. The factory fixes both addresses, the image hash and the adapter fingerprints as immutables. On `createAccount(policyId)` it verifies the bindings, copies and hashes both fragments, appends the typed constructor arguments and executes zero-value CREATE. The factory supplies `msg.sender` as owner and bubbles a constructor revert. No caller supplies executable bytes, a destination, a recipient or an initializer. The public account registration and event retain the existing shape. [Measurement prototype](../evidence/session7-size/SplitVaultFactory.sol)

The fork test used the actual 1952 venue bindings and the published vault sibling’s owner and policy. It checked a different account address, byte-for-byte identical deployed code by hash, correct owner and policy, zero operators and zero vault shares. The existing account retained its four mock shares. A second creation for that owner reverted. This is one local Foundry test against public historical state, with zero failed and zero skipped. Its gas counter covers the entire test, including both creations and assertions. It is unsuitable as an individual transaction estimate. [Fork comparison](../evidence/session7-size/SplitComparison.t.sol) · [Results](../evidence/session7-size/measurements.json)

A production candidate would need independent scrutiny of fragment creation/copying and failure propagation, code hash and length verification for both fragment addresses in the manifest, and runtime/initcode checks on all outputs at the release compiler settings. Benchmark first factory deployment and each subsequent account creation separately on the intended chain. Keep testing owner-only exit and risk-reducing repayment after an adapter or oracle outage.

### Clone initialization and upgrade assumptions

The current account embeds its owner, controller, pTokens, underlying tokens, adapter addresses, code hashes and oracle age in immutable runtime data. Its constructor checks the policy and writes the initial policy ID to storage. The sibling additionally binds the vault adapter, vault and underlying. A clone of this deployed implementation would read the original owner and bindings and start with empty clone storage. A viable clone version would need a new implementation designed for those semantics. [Base account constructor](../contracts/expansion/src/account/SentinelAccountV2.sol) · [Vault constructor](../contracts/expansion/src/vault/VaultSentinelAccountV2.sol)

A future design must initialize the clone atomically in the factory transaction, use the authenticated caller as owner, validate all policy and venue identities, reject repeat initialization, disable initialization on the implementation itself and make state-changing entrypoints require completed initialization. Set initialization state before any external interaction and register the clone only after validating its resulting state. Tests must cover a failed initialization rolling back creation and registration, reinitialization, independent balances and grants across users, and behavior during dependency outages. The fixed implementation address must resolve directly to code with a pinned hash. A beacon or upgradeable proxy as the target would give its administrator influence over all clone accounts.

ERC-1167 inherently uses DELEGATECALL. Even with a fixed destination, this changes the current v2 execution model and would require an explicit architecture decision. A clone’s runtime hash identifies its dispatcher and fixed implementation address. Ownership, grants, policy and asset bindings would also require account storage reads. This is a poor fit for a freeze-week change. [Standardized runtime and initialization model](https://eips.ethereum.org/EIPS/eip-1167)

## Migration consequences

A new factory is a distinct account namespace. The split prototype’s two fragment creations also advance the new factory’s CREATE nonce before its first account creation. Compute addresses from the actual deployment and verify `AccountCreated` and `accountOf(owner)`. An address derived for an earlier factory or a hypothetical CREATE2 salt is insufficient. CREATE2 address derivation also includes the deploying address and the initcode hash. [EIP-1014](https://eips.ethereum.org/EIPS/eip-1014)

Add a versioned manifest and supported-profile entry, preserve old factory discovery, and keep portfolios keyed by chain, factory and account address. The old account retains its positions, debt, grants and approval state. A user choosing the new profile creates a fresh account. To move assets, the owner revokes grants on the old account, repays or unwinds book positions under the applicable rules, redeems vault shares when liquid or exits in kind, then funds the new address and explicitly issues new grants. A new account cannot assume the old borrower’s debt, policy configuration or operator authorization. Preserve both receipt histories and help the owner verify each account independently. [V2 custody and authorization interfaces](coordination/INTERFACES_V2.md)

## Reproduce

From the repository root with the locked npm dependencies and Foundry available, run `node evidence/session7-size/measure.mjs`. The script uses isolated Git archives at both deployment source pins, solc 0.8.26, via IR, Paris EVM and 200 optimizer runs for the baseline. It compiles the one-run comparison separately, verifies public historical bytecode and runs the isolated split-factory test on a 1952 fork. It prints the measured JSON to stdout. All public RPC operations are reads. The temporary build tree is under the ignored `.research/` directory. [Measurement script](../evidence/session7-size/measure.mjs)
