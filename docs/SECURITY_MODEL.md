# Peridot development trust boundaries

- **Market creator.** Creates an isolated instance from the factory's approved pair, chooses bounded immutable limits, registers liquidity and activates borrowing. The owner can replace the market policy immediately with another registered market policy. Each pToken seals its administrative surface after initialization and pauses flash loans. One market cannot pledge another market's shares.
- **Registrar.** Approves processor addresses, checks compiler/config correspondence and can revoke trust. Registration checks code hash, pin counts, state, gate count, raw netlist hash and backward NAND wire references. Runtime checks registry eligibility and the processor's external code hash. A proxy can change its behavior through an implementation or dependency while preserving that code hash. Sponsor factory and beacon evidence must be checked independently. Dev governance permits immediate changes.
- **Processor.** Receives only packed, controller-derived risk data by STATICCALL. Its call budget is 1,500,000 gas and the adapter copies 96 return bytes. Only canonical dynamic ABI bytes with a single 0 or 1 output are valid. Unavailability stops applicable risk operations. Repayment and valid liquidation have no policy evaluation dependency.
- **Sentinel owner.** Sets the personal policy, repayment threshold and operator grant, and receives withdrawals. The account is bound to one factory-recognized market. A grant never changes the withdrawal recipient. An automated operation is atomic with the grant charge and settlement. Manual repayment remains available after grant or policy revocation.
- **Keeper.** A separate operator proposes one typed repayment using account funds. Exact allowances to the lending book are cleared after settlement. On-chain expiry, budget, funds, LTV and trigger are rechecked at execution. A failed simulation or ambiguous receipt cannot establish that a repayment succeeded.
- **Deployment.** The factory, controller, registry, Sentinel contracts and surrogate processor enforce the development chain IDs at construction. A chain ID alone does not authenticate an RPC. Manifest verification and actual receipt evidence are required. Read-only sponsor inspection and a forked fabrication have different provenance from public testnet deployment.

## Release status

Funded production deployment is blocked. The repo contains a development profile with immediate configuration, mock assets and mock USD feeds. A release needs a separately implemented governance delay, roles, verified assets and feeds, operational liquidation capacity and independent release testing. The local suite covers selected critical paths. It is not a production audit.
