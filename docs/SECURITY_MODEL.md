# Peridot Sentinel security model

- **Market creator.** Creates an isolated instance from the factory's approved pair, chooses bounded immutable limits, registers liquidity and activates borrowing. The owner can replace the market policy immediately with another registered market policy. Each pToken seals its administrative surface after initialization and pauses flash loans. One market cannot pledge another market's shares.
- **Registrar.** Approves processor addresses, checks compiler/config correspondence and can revoke trust. Registration checks code hash, pin counts, state, gate count, raw netlist hash and backward NAND wire references. Runtime checks registry eligibility and the processor's external code hash. A proxy can change its behavior through an implementation or dependency while preserving that code hash. Sponsor factory and beacon evidence must be checked independently. Dev governance permits immediate changes.
- **Processor.** Receives only packed, controller-derived risk data by STATICCALL. Its call budget is 1,500,000 gas and the adapter copies 96 return bytes. Only canonical dynamic ABI bytes with a single 0 or 1 output are valid. Unavailability stops applicable risk operations. Repayment and valid liquidation have no policy evaluation dependency.
- **Sentinel owner.** Sets the personal policy, repayment threshold and operator grant, and receives withdrawals. The account is bound to one factory-recognized market. A grant never changes the withdrawal recipient. An automated operation is atomic with the grant charge and settlement. Manual repayment remains available after grant or policy revocation.
- **Keeper.** A separate operator proposes one typed repayment using account funds. Exact allowances to the lending book are cleared after settlement. On-chain expiry, budget, funds, LTV and trigger are rechecked at execution. A failed simulation or ambiguous receipt cannot establish that a repayment succeeded.
- **Deployment.** The factory, controller, registry, Sentinel contracts and surrogate processor enforce the development chain IDs at construction. A chain ID alone does not authenticate an RPC. Manifest verification and actual receipt evidence are required. Read-only sponsor inspection and a forked fabrication have different provenance from public testnet deployment.

## Release status

Funded production deployment is blocked. The repo contains a development profile with immediate configuration, mock assets and mock USD feeds. A release needs a separately implemented governance delay, roles, verified assets and feeds, operational liquidation capacity and independent release testing. The local suite covers selected critical paths. It is not a production audit.

## Studio market policy publication

On a registry exposing the v1.2 commitment, any wallet can publish the SDK's `market-max-ltv-v0` policy for an integer threshold from 0 through 10000 bps and either reserve setting. The contract checks a Merkle proof for the threshold, reserve flag, canonical config hash and exact netlist hash. It then matches the actual circuit dimensions, raw bytes and NAND references on a registrar-trusted processor. The registry owner retains exclusive authority over processor trust and general registration, including account policies. A publisher acquires no market, account or processor authority.

The leaf index is `2 * maxLtvBps + Number(requireCashReserve)`. Each leaf hashes `abi.encodePacked(uint16(maxLtvBps),bool(requireCashReserve),bytes32(configHash),bytes32(netlistHash))`. Fifteen ordered sibling hashes give the path to `MARKET_TEMPLATE_ROOT()`. The proof is portable across deployments of the same template version. Each policy ID also binds the chain, registry, processor and actual circuit ID. An SDK build and `node packages/circuit-sdk/scripts/studio-tree.mjs --check` reconstruct all 20,002 leaves and verify the committed root. An incompatible compiler or root requires a new deployment and an interface notice.

A project wallet can perform the following sequence.

1. Verify chain, code, processor provenance, the factory's registry address and equality between `MARKET_TEMPLATE_ROOT()` and the SDK's `STUDIO_MARKET_ROOT`. Call `studioMarketTemplate(bps, requireCashReserve)` for the spec, compiled bytes and proof.
2. Read `marketTemplatePolicy(processor, configHash)`. If the lookup is empty on a development-reference deployment, submit the compiled bytes to `DevelopmentReferenceProcessor.addReferenceCircuit` and decode `ReferenceCircuitAdded` from that processor's receipt. A sponsor processor requires its own fabricated circuit ID and matching bytes. The development interpreter is a Peridot test fixture.
3. Call `registerMarketTemplate(processor,circuitId,bps,requireCashReserve,netlistHash,configHash,proof)` if registration is needed. The first successful publication indexes the canonical entry. A concurrent publication can reuse it. After confirmation, resolve the ID again from the registry, verify its entry, and call `requirePolicy(id,0)` to check current trust. Direct registrar publication of the exact same entry can also be indexed.
4. Submit `MarketFactory.createMarket` from the intended market owner, or call `setPolicy(id)` on a controller that wallet owns. A newly created market starts inactive. Studio selection does not change lending or liquidation limits, balances or approvals.

The local receipt runner accepts an unforked loopback deployment manifest, checks the capability root and uses the third unlocked Anvil account as the project owner. From the repository root run `node contracts/script/studio-local-demo.mjs http://127.0.0.1:18545 packages/chain-config/deployments/31337.json 6234 true` against a v1.2 local deployment. It emits the hashes, market addresses and receipts. A historical v1 registry requires a fresh deployment before this flow is available.

## Sentinel accounts v2 and Connect

The expansion factory fixes the lending adapter, swap adapter and execution policy at deployment. The account pins code hashes and the external route. An operator's grant identifies operator, adapter, action and input asset. Expenditure debits a per-call and remaining cumulative budget atomically. The owner can revoke it. Swaps fix the recipient to the calling account, clear both layers of allowance and verify token deltas. Lending settlement occurs on the account's own books. The trust assumptions include exact-transfer tokens, the configured router and oracle, and the implementation behind every pinned proxy. A proxy code hash alone cannot establish its future implementation.

Connect's signing process is a separate trust boundary. Its single execute tool accepts a locally recorded proposal ID. Its signing authority is the dedicated operator for the manifest-verified account's zero-value autoRepay() call on 1952. The owner controls the on-chain grant and trigger. Repayment can change between simulation and inclusion. Report actual confirmed settlement and preserve the transaction hash across interruptions. [Expansion interface](coordination/INTERFACES_V2.md)

## Emergency revocation scope

Each v2 account keeps its own authorization epoch. All five base operator actions and all three vault actions charge a grant from the current epoch. Changing the epoch invalidates every prior grant in one storage update. External callers of the swap router can spend only their own input or an explicit allowance. The account clears its external allowances at settlement. The Peridot and vault bindings expose reads and do not forward withdrawals. The in-kind share exit, underlying withdrawals and permission changes require the account owner.

The public M4 keeper and the original Connect tool operate on a **separate v1 account**. To stop that account's automation, revoke its v1 operator and clear its auto-repay trigger. A v2 emergency stop affects only the account on which the owner calls it. Current v2 Connect proposals still face the on-chain grant check at inclusion and can revert if the owner changes the epoch after simulation. [Account interface](coordination/INTERFACES_V2.md)
